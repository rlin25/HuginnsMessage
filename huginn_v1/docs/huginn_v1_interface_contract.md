# Huginn v1 — Interface Contract Document

**Status:** Implementation complete. Phase 7 (Feedback Loop) complete.
**Last updated:** May 2026
**Source of truth:** `huginn_v1_design_decisions.md` (Decisions 1–34)
**Purpose:** Defines every component's inputs, outputs, and data types. This is the stable contract Claude Code builds against. No implementation decision should contradict this document.

---

## How to Use This Document

Every component in Huginn has a defined boundary. This document specifies what crosses that boundary in both directions — nothing more, nothing less. When implementing any component, the contract for that component is the authoritative specification. If the implementation requires something not specified here, that is a signal to return to the design phase, not to make an ad-hoc decision during implementation.

## Component 1 — Exception Schema (`models/exception.py`)

This is the foundation. Every other component either consumes this schema or produces records that reference it.

### Pydantic Model

```python
from pydantic import BaseModel, model_validator
from uuid import UUID
from datetime import datetime
from enum import Enum

class ExceptionType(str, Enum):
    settlement_mismatch = "settlement_mismatch"

class SettlementMismatchSubType(str, Enum):
    price_mismatch = "price_mismatch"
    quantity_mismatch = "quantity_mismatch"
    wrong_settlement_date = "wrong_settlement_date"

class Severity(str, Enum):
    low = "low"
    medium = "medium"
    high = "high"

class TradeException(BaseModel):
    exception_id: UUID
    trade_id: str
    type: ExceptionType
    sub_type: SettlementMismatchSubType
    description: str
    timestamp: datetime
    severity: Severity

    @model_validator(mode="after")
    def validate_sub_type_scope(self):
        # In v1 only settlement_mismatch is valid, so all SettlementMismatchSubType
        # values are valid. This validator becomes meaningful in v2 when additional
        # ExceptionType values are added with their own sub_type enums.
        return self
```

### Field Specifications

| Field | Type | Required | Notes |
|---|---|---|---|
| `exception_id` | `UUID` | Yes | Uniquely identifies this exception in Huginn's pipeline |
| `trade_id` | `str` | Yes | References the originating trade — format is not standardized |
| `type` | `ExceptionType` enum | Yes | Must be `settlement_mismatch` in v1 — all others rejected |
| `sub_type` | `SettlementMismatchSubType` enum | Yes | Must match parent type — enforced by model validator |
| `description` | `str` | Yes | Natural language description — used in Mimir query construction |
| `timestamp` | `datetime` | Yes | ISO 8601 — enables SQLite date range queries |
| `severity` | `Severity` enum | Yes | `low`, `medium`, or `high` — metadata only in v1, reasoning input in v2 |

### Validation Behavior

- Invalid `type` value → Pydantic raises `ValidationError` before the agent is called
- Invalid `sub_type` value → Pydantic raises `ValidationError` before the agent is called
- Invalid `sub_type` for parent `type` → model validator raises `ValidationError`
- Missing required field → Pydantic raises `ValidationError`

## Component 2 — API Layer (`api/main.py`)

The API layer is the only entry point to the system. All validation happens here before anything else runs.

### Endpoint 1 — POST /exceptions

**Purpose:** Accept a trade exception, validate it, hand it to the agent, return a job ID.

**Request body:** `TradeException` (see Component 1)

**Success response (HTTP 200):**
```json
{
  "job_id": "uuid",
  "status": "received",
  "exception_id": "uuid",
  "timestamp": "datetime"
}
```

**Validation error response (HTTP 422):**
```json
{
  "detail": [
    {
      "loc": ["body", "field_name"],
      "msg": "error description",
      "type": "error_type"
    }
  ]
}
```

**Notes:**
- `job_id` is a new UUID generated by the API layer, distinct from `exception_id`
- In v1 processing is synchronous — the result is available immediately
- The fake async pattern means the interface is forward-compatible with v2 async processing

---

### Endpoint 2 — GET /exceptions/{job_id}

**Purpose:** Retrieve the full agent decision for a previously submitted exception.

**Path parameter:** `job_id` (UUID)

**Success response (HTTP 200):**
```json
{
  "job_id": "uuid",
  "exception_id": "uuid",
  "outcome": "auto_resolve | escalate",
  "confidence_score": "float (0.0–1.0)",
  "reasoning_trace": "str",
  "resolution_steps": "str",
  "retrieved_document_id": "str | null",
  "escalation_reason": "str | null",
  "timestamp": "datetime"
}
```

**Field notes:**
- `retrieved_document_id` is `null` on the mandatory escalation fast-exit path — Mimir was never called
- `escalation_reason` is `null` when `outcome` is `auto_resolve`
- `escalation_reason` contains the triggered keyword when outcome is from the fast-exit path (e.g. `"mandatory escalation keyword detected: sanctions"`)
- `escalation_reason` contains a confidence explanation on the standard path escalation (e.g. `"confidence score 0.43 below threshold 0.75"`)
- `resolution_steps` is populated on the standard path only — null on fast-exit

**Not found response (HTTP 404):** job_id does not exist in the result store

---

### Endpoint 3 — GET /escalations

**Purpose:** Return the full current escalation queue — the human reviewer's inbox.

**No request parameters.**

**Success response (HTTP 200):**
```json
{
  "escalations": [
    {
      "job_id": "uuid",
      "exception_id": "uuid",
      "trade_id": "str",
      "type": "str",
      "sub_type": "str",
      "outcome": "escalate",
      "confidence_score": "float | null",
      "reasoning_trace": "str | null",
      "escalation_reason": "str",
      "retrieved_document_id": "str | null",
      "timestamp": "datetime"
    }
  ]
}
```

**Notes:**
- `confidence_score` and `reasoning_trace` are null for fast-exit escalations — the LLM was never called
- `retrieved_document_id` is null for fast-exit escalations — Mimir was never called
- Returns empty list `{"escalations": []}` when queue is empty, not a 404

## Component 3 — LangGraph Agent (`agent/`)

### Agent State Object (`agent/state.py`)

The state object flows through every node. Each node receives the full state and returns a partial update. Fields accumulate or replace as noted.

```python
from typing import TypedDict

class AgentState(TypedDict):
    # Input — set at entry, never modified
    exception: dict                          # Full TradeException as dict
    job_id: str                              # Assigned by API layer

    # Set by classification node
    exception_type: str                      # Validated type value
    exception_sub_type: str                  # Validated sub_type value
    triggered_keyword: str | None            # Populated if fast-exit fires

    # Set by retrieval node (standard path only)
    retrieved_chunks: list[dict]             # List of chunk dicts from Mimir
    retrieved_document_id: str | None        # ID of primary retrieved document

    # Set by reasoning node (standard path only)
    confidence_score: float | None           # LLM-produced float 0.0–1.0
    reasoning_trace: str | None              # LLM-produced reasoning
    resolution_steps: str | None             # LLM-produced resolution steps
    llm_raw_response: str | None             # Raw LLM response before JSON parsing

    # Set by decision node
    outcome: str | None                      # "auto_resolve" or "escalate"
    escalation_reason: str | None            # Populated on escalation

    # Debugging
    current_node: str                        # Name of currently executing node
```

[Updated post-implementation: Imports reduced to `from typing import TypedDict` only — `Annotated`, `from operator import add`, and `UUID` were not used in the implementation. `job_id` type changed from `UUID` to `str` — the API layer generates the job ID as a `str(uuid.uuid4())` and stores it as a string throughout. `llm_raw_response: str | None` added — the reason node stores the raw Claude API response before JSON parsing for full-fidelity audit logging and debugging; this field was present in `agent/state.py` but missing from the contract definition.]

### Node Specifications

Each node is a pure function: `(AgentState) -> dict` (partial state update).

| Node | Input fields read | Output fields written | Notes |
|---|---|---|---|
| `classify` | `exception` | `exception_type`, `exception_sub_type`, `triggered_keyword`, `current_node` | Detects keywords; sets triggered_keyword if found |
| `retrieve` | `exception_sub_type`, `exception["description"]` | `retrieved_chunks`, `retrieved_document_id`, `current_node` | Standard path only; calls `mimir.retrieve()` |
| `reason` | `exception`, `retrieved_chunks` | `confidence_score`, `reasoning_trace`, `resolution_steps`, `llm_raw_response`, `current_node`; also `escalation_reason` on API failure | Standard path only; calls Claude API. On failure: all LLM fields null, `escalation_reason = "system_error: ..."` |
| `decide` | `confidence_score` | `outcome`, `escalation_reason`, `current_node` | Compares score against threshold (0.75); escalates if `confidence_score` is null |
| `escalate_fast_exit` | `triggered_keyword` | `outcome`, `escalation_reason`, `current_node` | Fast-exit path only; sets `outcome = "escalate"`, records keyword as reason |
| `log_result` | All fields | None (side effect only) | Calls `logger.log()` |

[Updated post-implementation: `escalate` renamed to `escalate_fast_exit` — matches the actual function name in `agent/nodes.py`. `reason` node output expanded to include `llm_raw_response` and the failure-path `escalation_reason` — the reason node writes these fields directly when the Claude API call throws an exception (Decision 33).]

### Graph Paths

**Path 1 — Invalid type exit:**
Fires at API layer (Pydantic validation), not inside the graph. The agent never receives an invalid type.

**Path 2 — Mandatory escalation fast-exit:**
`classify` → (keyword found) → `escalate_fast_exit` → `log_result`
- `retrieved_chunks` remains empty
- `retrieved_document_id` is null
- `confidence_score` is null
- `reasoning_trace` is null

**Path 3 — Standard path:**
`classify` → (no keyword) → `retrieve` → `reason` → `decide` → (`auto_resolve` or `escalate`) → `log_result`

## Component 4 — Mimir Retriever (`mimir/retriever.py`)

### Public Interface

```python
def retrieve(query: str, top_k: int = 3) -> list[dict]:
    ...
```

**This is the only public function in the Mimir component.** Everything else in `mimir/` is internal implementation detail.

### Input

| Parameter | Type | Default | Notes |
|---|---|---|---|
| `query` | `str` | Required | Constructed as `"{sub_type}: {description}"` by the agent |
| `top_k` | `int` | `3` | Maximum number of chunks to return |

### Output

Returns a list of dicts, each with the following fields:

| Field | Type | Notes |
|---|---|---|
| `text` | `str` | The chunk content — passed to the LLM reasoning prompt |
| `document_id` | `str` | Identifies the source SOP document |
| `sub_type` | `str` | The sub_type this document covers |
| `similarity_score` | `float` | Semantic similarity to the query — provided natively by Chroma |

### Query Construction (called by agent, not Mimir)

The agent constructs the query string before calling Mimir:
```python
query = f"{exception['sub_type']}: {exception['description']}"
```

### Behavior Notes

- Returns an empty list if the Chroma index is empty or unavailable
- Does not raise exceptions for no-results — the agent handles empty retrieval
- Never called on the mandatory escalation fast-exit path
- `document_id` of the first (highest similarity) chunk is used as `retrieved_document_id` in the audit log and API response

## Component 5 — LLM Reasoning (`agent/nodes.py` — reason node)

### Claude API Call Inputs

| Input | Source | Notes |
|---|---|---|
| Exception payload | `state["exception"]` | Full dict |
| Retrieved chunks | `state["retrieved_chunks"]` | List of chunk dicts from Mimir |
| Scoring rubric | Hardcoded in node | Defines high vs low confidence criteria |

### Prompt Structure

The reasoning prompt contains three sections in order:
1. The scoring rubric — defines what constitutes high vs low confidence and how to weight inputs
2. The retrieved SOP chunks — formatted as labeled context
3. The exception payload — formatted as labeled input

The LLM is instructed to respond with structured JSON only, no preamble.

### Required LLM Output Schema

```json
{
  "confidence_score": 0.82,
  "reasoning_trace": "Step-by-step explanation of how the score was reached",
  "resolution_steps": "Specific steps to resolve this exception per the SOP"
}
```

| Field | Type | Constraints |
|---|---|---|
| `confidence_score` | `float` | Must be between 0.0 and 1.0 |
| `reasoning_trace` | `str` | Must be present and non-empty |
| `resolution_steps` | `str` | Must be present and non-empty |

### Escalation Decision (called by decide node, not reason node)

```python
ESCALATION_THRESHOLD = 0.75

if confidence_score >= ESCALATION_THRESHOLD:
    outcome = "auto_resolve"
else:
    outcome = "escalate"
    escalation_reason = f"confidence score {confidence_score} below threshold {ESCALATION_THRESHOLD}"
```

The LLM does not make the escalation decision — it produces the confidence score. The decision is deterministic code.

## Component 6 — Audit Logger (`logger/audit.py`)

### Public Interface

```python
def log(event: dict) -> None:
    ...
```

**This is the only public function in the logger component.**

### Input — Event Dict Fields

The event dict passed to `log()` must contain:

| Field | Type | Always present | Notes |
|---|---|---|---|
| `job_id` | `str` | Yes | |
| `exception_id` | `str` | Yes | |
| `trade_id` | `str` | Yes | |
| `type` | `str` | Yes | |
| `sub_type` | `str` | Yes | |
| `description` | `str` | Yes | |
| `timestamp` | `str` | Yes | Original exception timestamp |
| `severity` | `str` | Yes | Metadata only in v1 |
| `outcome` | `str` | Yes | `"auto_resolve"` or `"escalate"` |
| `triggered_keyword` | `str \| None` | Yes | Null if standard path |
| `retrieved_chunks` | `list[dict]` | Yes | Empty list if fast-exit path |
| `retrieved_document_id` | `str \| None` | Yes | Null if fast-exit path |
| `confidence_score` | `float \| None` | Yes | Null if fast-exit path |
| `reasoning_trace` | `str \| None` | Yes | Null if fast-exit path |
| `resolution_steps` | `str \| None` | Yes | Null if fast-exit path |
| `escalation_reason` | `str \| None` | Yes | Null if auto-resolve |
| `llm_raw_response` | `str \| None` | Yes | Raw LLM response before parsing; null if fast-exit |
| `decision_timestamp` | `str` | Yes | When Huginn made the decision |

### Output — Write Destinations

The logger writes to all applicable destinations for every call:

1. **Always:** Appends to `logs/audit.jsonl`
2. **Always:** Inserts row into `logs/audit.db` (SQLite)
3. **If `outcome == "escalate"`:** Appends to `logs/escalation_queue.jsonl`

The caller does not specify destinations. Routing is internal to the logger.

### SQLite Schema

```sql
CREATE TABLE audit_log (
    job_id TEXT PRIMARY KEY,
    exception_id TEXT,
    trade_id TEXT,
    type TEXT,
    sub_type TEXT,
    outcome TEXT,
    confidence_score REAL,
    triggered_keyword TEXT,
    retrieved_document_id TEXT,
    escalation_reason TEXT,
    decision_timestamp TEXT,
    exception_timestamp TEXT,
    severity TEXT,
    full_event_json TEXT
);
```

`full_event_json` stores the complete event dict as a JSON string, enabling full reconstruction without field migration when new fields are added in v2.

## Component Interaction Summary

```
HTTP Request
    ↓
[API Layer] — validates TradeException schema
    ↓
[Agent — classify node] — detects type and keywords
    ↓
    ├── keyword found → [Agent — escalate_fast_exit node] → [Logger]
    └── no keyword → [Mimir — retrieve()] → [Agent — reason node]
                                                    ↓
                                             [Agent — decide node]
                                                    ↓
                                         ┌──────────┴──────────┐
                                    auto_resolve            escalate
                                         └──────────┬──────────┘
                                                    ↓
                                               [Logger]
                                                    ↓
                                         audit.jsonl + SQLite
                                         + escalation_queue.jsonl (if escalated)
```

## What This Document Does Not Specify

The following are implementation details that belong in Claude Code, not in this contract:

- The exact wording of the LLM scoring rubric
- The specific chunking strategy for SOP documents
- The embedding model configuration
- The format of log messages at individual nodes
- Error handling for Claude API timeouts or failures
- The specific text of Pydantic validation error messages
- Internal variable names within any component

These details are resolved during implementation and fed back into the project via the Phase 7 feedback loop.
